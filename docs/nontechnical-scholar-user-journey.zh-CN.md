# Survey Scale Review 非技术学者用户旅程评估

**状态：** 待评审

本文从一个实际学者，尤其是不太懂 GitHub、命令行、Codex Skill 安装和 Python 脚本的学者视角，评估 `survey-scale-review` 从发现、理解、安装、准备材料、运行、阅读输出到采纳建议的完整使用过程。目标不是再增加功能，而是识别哪些地方会让真实用户放弃、误用或过度信任。

> 📖 **核心判断**
>
> 当前版本已经比第一版更像一个可公开分享的工具，但对非技术学者来说，最大障碍不是“这个 Skill 能不能审问卷”，而是“我怎么开始用、我应该准备什么、我看完输出后该怎么做”。因此，下一轮优化应重点降低进入门槛、增加示例、提供无命令行路径，并明确研究者保留最终判断。

## 一、潜在用户画像

| 用户类型 | 可能需求 | 技术能力 | 最可能卡住的地方 |
|---|---|---|---|
| 组织行为学/管理学教师 | 检查 RA 整理的英文量表和中文问卷 | 可能会用 AI，但不熟 GitHub/命令行 | 不知道如何安装 Skill，不知道模板怎么填 |
| 博士生/研究生 | 做论文调研问卷，担心翻译和改编问题 | 可能会用 ChatGPT/Codex，但经验不稳定 | 不知道该给 AI 哪些信息 |
| 研究助理 | 按老师要求整理量表并初步自查 | Excel 熟练，技术能力不一 | 不知道问题清单里的 P0/P1 怎么处理 |
| 跨学科 AI at work 研究者 | 把成熟量表改编到 AI 场景 | 研究设计熟，但 OB 量表经验不一 | 容易把“改编”做成“自编” |
| 英文用户 | 想检查 translated/adapted scales | 不一定懂中文 | 默认输出中文可能让他们疑惑 |

## 二、完整使用流程与风险点

### 1. 发现仓库

用户可能通过 GitHub 搜索、朋友推荐、README 链接或 Codex Skill 分享看到项目。

当前优势：

- 仓库名称 `survey-scale-review` 清楚。
- README 关键词覆盖了 organizational behavior、survey scale review、scale adaptation、Chinese translation 等。
- 中英文文档都有。

潜在问题：

| 风险 | 说明 | 建议 |
|---|---|---|
| 不知道这是 Codex Skill | 很多学者不知道 Skill 是什么 | README 开头加一句“需要在 Codex 中使用；不是独立网页工具” |
| GitHub 页面看起来仍偏技术 | 学者可能看到 clone、pip 就退缩 | 增加 “For non-technical users” 快速说明 |
| 没有视觉预览 | 用户不知道输出长什么样 | 放一张 HTML issue table 截图或示例截图 |

### 2. 判断是否适合自己

学者会问：“我的问卷不是 Excel 模板，能不能用？”“我的量表是中文原版，也能不能用？”“我没有英文原题怎么办？”

当前 README 已经说明可以用非模板文件，但还可以更明确。

建议增加一个 “Can I use this if...?” 区块：

| 用户疑问 | 建议回答 |
|---|---|
| 我的问卷不是模板格式，可以吗？ | 可以，先让 Skill 推断结构并列出缺失信息 |
| 我只有 Word/问卷星文本，可以吗？ | 可以，但结构化程度越低，输出越需要人工确认 |
| 我没有英文原题，可以吗？ | 可以做发放前检查，但无法完整判断翻译和改编等价性 |
| 我使用的是中文成熟量表，可以吗？ | 可以重点检查填写体验、指代、时间点和配对结构 |
| 我不是 OB 研究，可以吗？ | 可以，但评估标准主要面向 OB/管理学/心理测量 |

### 3. 安装和启动

这是非技术用户最大的断点。

当前流程需要：

1. 知道什么是 Codex Skill。
2. 会把仓库 clone 到 `~/.codex/skills/`。
3. 知道要重启 Codex 会话。

潜在问题：

| 风险 | 影响 | 建议 |
|---|---|---|
| 不会使用命令行 | 直接无法安装 | 增加“如果你不会安装，把仓库链接发给 Codex，让 Codex 帮你安装”的说明 |
| 不知道 `~/.codex/skills` 是什么 | 不理解安装路径 | 用自然语言解释“这是 Codex 存放自定义技能的文件夹” |
| 安装后当前会话识别不到 | 误以为失败 | 明确说明“安装后新开一个 Codex 会话” |
| 不知道是否安装成功 | 无反馈 | 增加测试 prompt：“请列出 $survey-scale-review 的使用方式” |

建议 README 增加一个非技术安装路径：

```text
If you do not use the command line, open Codex and say:
"Please install this Codex skill from https://github.com/gtskevin/survey-scale-review into my local skills folder."
```

中文：

```text
如果你不会使用命令行，可以在 Codex 中直接说：
“请帮我把 https://github.com/gtskevin/survey-scale-review 安装到我的本地 Codex skills 文件夹。”
```

### 4. 准备材料

真实学者的材料通常很混乱：

- 一个 Excel 里有变量和条目，但列名不标准。
- 一个 Word 里已经排成正式问卷。
- RA 给了英文量表、中文翻译和来源，但没有时间点。
- 只有问卷星导出的题目，没有英文原文。
- 有些量表是从中文论文中借来的，没有英文 source item。

当前模板是有帮助的，但仍可能带来一个误解：用户以为必须先整理成模板才能用。

建议在 README 和中文文档中强调三层输入：

| 层级 | 用户状态 | Skill 应做什么 |
|---|---|---|
| 最低门槛 | 直接上传现有文件 | 先推断结构，列出缺失信息 |
| 推荐门槛 | 使用模板整理 | 做完整评估 |
| 高质量门槛 | 同时提供英文原题、中文题项、来源、填写者、时间点、改编说明 | 做更可靠的翻译、改编和审稿解释性评估 |

### 5. 使用模板

模板目前提供了 Excel 和 CSV，这是好的。但非技术学者可能还会遇到：

| 问题 | 说明 | 建议 |
|---|---|---|
| 不知道 instruction row 和 item row 区别 | 指导语和条目可能混在一起 | 模板中增加颜色或更明确示例 |
| 不知道量表类型怎么选 | 成熟直译/成熟改编/高度改编界限不清 | 增加一个小表解释五类量表 |
| 不知道来源怎么填 | 文献引用格式不一致 | 提供最小格式：作者、年份、题名、期刊 |
| 不知道反向题怎么标 | Reverse coded 信息可能丢失 | 在备注列示例中写 `Reverse-coded source item; rewritten positively` |
| 不知道新增题项怎么标 | 高改编量表容易混在成熟量表里 | 在备注中标 `new item` 或 `added global item` |

模板优化建议：

1. 在 Excel 模板中增加一个 `Guide` sheet，解释每列怎么填。
2. 在 `Variables` sheet 中保留 5 个示例：成熟直译、成熟改编、自编、高度改编、混合量表。
3. 在 `Questionnaire` sheet 中加入一条反向题正向化示例。
4. 增加一个空白可复制区域，让用户从第 10 行开始填自己的问卷。

### 6. 启动审查

用户可能不知道该怎么问。

当前 README 提供了示例 prompt，但可以进一步按场景提供：

| 场景 | 建议 prompt |
|---|---|
| 我第一次用 | “请先判断这个问卷文件结构是否足够做完整审阅，不够的话列出缺失信息。” |
| RA 刚整理完 | “先做快速质检，只看条目数、填写者、时间点、来源和占位符。” |
| 我准备正式发放 | “做发放前终检，不要大幅重写题项，只找阻断问题和填写歧义。” |
| 我担心改编被审稿人质疑 | “重点检查改编量表是否能向审稿人解释，并给方法部分写法建议。” |
| 我想优化中文表达 | “在不改变构念含义的前提下，给出中文修改建议和理由。” |

建议增加一个 `Prompt cookbook` 文档，降低用户不知道怎么开口的问题。

### 7. 阅读输出

HTML 问题清单已经更友好，但学者可能仍会有这些困惑：

| 困惑 | 原因 | 建议 |
|---|---|---|
| P0/P1/P2/P3 不知道先处理哪个 | 优先级概念对非技术用户不直观 | 在 HTML 顶部加“先处理 P0，再处理 P1” |
| 不知道哪些可以让 RA 改，哪些必须老师判断 | reviewer_action 已有，但可以更明确 | 用“RA 可直接处理 / 研究者必须确认 / 仅提示” |
| 问题太多时焦虑 | 一次性列很多条 | 报告先给“前三个必须处理的问题” |
| 建议文本和当前文本太长 | 阅读负担大 | 增加“简短问题摘要”列 |
| 不知道如何采纳修改 | HTML 不可直接勾选 | 可选生成“采纳决策表”或优化版对照表 |

### 8. 采纳修改

这是研究质量风险最高的阶段。用户可能会把 AI 建议直接全盘接受。

建议输出中明确区分：

| 建议类型 | 处理方式 |
|---|---|
| 发放阻断 | RA 可直接修，如占位符、行号、缺失来源 |
| 表达润色 | 可采纳，但检查是否改变构念含义 |
| 改编合理性 | 研究者必须判断 |
| 自编/高度改编量表 | 建议专家审阅、预测试或后续信效度检验 |
| 方法写作建议 | 可作为草稿，不能直接视为最终论文表述 |

### 9. 与研究助理协作

很多老师真正的使用方式不是自己逐项修改，而是把结果交给 RA。

当前 HTML 输出适合阅读，但对协作闭环还不够。

建议增加一个 “RA workflow”：

1. 老师或 RA 上传初版问卷。
2. Skill 生成 HTML 问题清单。
3. RA 先处理 `RA 可直接处理` 的问题。
4. 老师处理 `研究者必须确认` 的问题。
5. 修改后再次运行 `pre-launch check`。
6. 正式发放。

可考虑增加一个状态字段说明：

| 状态 | 含义 |
|---|---|
| 待处理 | 尚未修改 |
| RA 已处理 | RA 已修，等待老师确认 |
| 研究者已确认 | 老师已确认 |
| 不采纳 | 明确保留原写法 |
| 需讨论 | 涉及构念或改编策略 |

### 10. 信任与边界

非技术用户也可能非方法专家，容易把 Skill 的输出看成“审稿保证”。

README 已有 “What This Skill Does Not Do”，但在实际输出中也应反复提醒：

- 这不是信效度证明。
- 这不是文献原文核验，除非用户提供原文。
- 这不是伦理审查或 IRB 审查。
- 高度改编和自编量表仍需预测试和统计检验。
- AI 修改建议是审稿辅助，不是最终理论判断。

## 三、建议的下一轮产品优化

### A. README 层面

优先级高：

1. 增加 “For non-technical users” 安装说明。
2. 增加 “Can I use this if...?” 常见问题。
3. 增加 “Prompt cookbook” 小节或单独文件。
4. 增加输出截图或示例 HTML 链接。

优先级中：

1. 增加 “RA workflow”。
2. 增加 “How to interpret P0-P3”。
3. 增加 “What information improves review quality”。

### B. 模板层面

优先级高：

1. Excel 模板增加 `Guide` sheet。
2. 增加反向题正向化示例。
3. 增加自编/高度改编示例。
4. 增加 “从第几行开始填自己的内容” 的提示。

优先级中：

1. 做一个最小版模板，只包含必填列。
2. 做一个完整研究版模板，包含问卷编号、配对 ID、量表类型、改编说明和计分方向。

### C. Skill 输出层面

优先级高：

1. HTML 顶部增加执行摘要：P0/P1 数量、是否建议发放、前三个必须处理问题。
2. Issue 表增加“简短问题摘要”列。
3. 对每个问题标明“RA 可直接处理 / 研究者必须确认 / 仅提示”。
4. 默认最后给出“下一步建议 prompt”。

优先级中：

1. 生成 RA 任务清单。
2. 生成研究者决策清单。
3. 生成发放前终检 checklist。

### D. 使用体验层面

优先级高：

1. 给不会命令行的用户一条明确安装路径。
2. 明确说明“不用模板也可以先用”。
3. 引导用户先做快速结构检查，再做完整审阅。

优先级中：

1. 增加一个 sample output 文件夹。
2. 放一个匿名示例问卷和对应输出。
3. 在 GitHub README 顶部放示例 HTML 截图。

## 五、总体结论

当前仓库已经具备公开分享的基础，但如果目标是让更多非技术学者真正使用，而不是只 star，下一轮应该从“工具说明”转向“使用陪伴”。

最关键的改进不是增加更多评估维度，而是把用户带过三个门槛：

1. **我能不能用？**  
   回答：可以，不用模板也能先检查。

2. **我怎么开始？**  
   回答：给出非技术安装方式、模板和示例 prompt。

3. **我看完结果怎么办？**  
   回答：先修 P0，再处理 P1；RA 处理格式和占位符，研究者判断改编和构念问题。

如果这三点打通，`survey-scale-review` 会更像一个真实可用的研究工作流工具，而不只是一个代码仓库。
